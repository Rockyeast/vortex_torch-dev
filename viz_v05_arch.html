这个项目在解决什么问题

大模型每生成一个新 token，都要回头看前面的历史。历史越长，看一遍越慢。vortex_torch 做的事是：先把历史切成很多块，再快速挑出最值得看的块，让注意力计算少看一点历史、跑得更快。

你写规则
“哪些历史块重要？”

源码名：`vFlow / vFlowMLA`。你写一个策略，告诉框架怎么给历史块打分、怎么挑块。

down
拆成步骤
求平均、算相似度、取前 K 个

源码里会看到 `Mean / GeMM / Max / topK`。它们就是可追踪的小步骤。

down
记成图
把 Python 写法变成计算流程图

源码名：`trace -> graph`。先不真的算，只记录“第一步做什么、第二步做什么”。

down
变快
生成 GPU 上跑的高速代码

源码名：`Triton / CUDA / custom_ops`。推理时不能慢慢跑 Python，所以要编译。

down
真正生成
用挑出来的历史块做 attention

源码名：`FlashInfer / TRT-LLM / MLA`。这些后端负责真正的注意力计算。

先记住这几个词

token

模型一次生成或读取的小单位。中文里可能是一个字、一个词片段，英文里可能是半个词。

K/V cache

历史内容的缓存。模型后面生成新 token 时，会反复回头看这里。

block / page

把历史按块整理。Vortex 主要按 block 选择“哪些历史值得看”。

sparse attention

不看全部历史，只看一部分重要历史。这里的 sparse 就是“稀疏地看”。

最后由谁真正算 attention

FlashInfer

常用的高性能 attention 库。Vortex 把选中的历史块整理成它能读的格式。

TRT-LLM

NVIDIA 推理栈相关路径。它需要另一种“历史块列表”格式。

代码分析理解模块

这里不按源码行号硬读，而是按“这个文件回答了什么问题”来读。第一站是 `flow/algorithms.py`，因为它最直接展示 Vortex 怎么定义选块策略。

最合适的读法：三问法

1. 先找 register 名字

`@register("block_sparse_attention")` 说明这个策略运行时叫什么名字。

2. 看 create_cache

它回答“每个历史块要额外存什么摘要”。比如 centroid、max/min、v_energy。

3. 看 forward_cache

它回答“当前 token 写进 K/V 后，怎么更新仓库里的摘要”。

4. 看 forward_indexer

它回答“怎么用 query 和摘要打分，最后 topK 选哪些历史块”。

不要一开始陷进每个算子的实现。先把每个策略压缩成一句话：存什么摘要、怎么更新、怎么打分、最后怎么选。

普通 K/V 策略可视化

每个策略都还是三问法：存什么摘要、怎么用 query 打分、怎么 topK。区别在于“摘要长什么样”和“多个 head / sub-block / 特征维怎么合并”。

这是最基础的 centroid 策略：每块历史存一个平均 key，当前 query/head 先平均，再和所有历史块代表比相似度。
对：中间先得到 H_q × page 数个分数。之后才把多个 head 对同一个 page 的分数合并，变成每个 page 一个最终分数，再 topK。
QUEST 的核心是“这个历史块最多可能多相关”，所以存的是每个维度的 max/min，而不是 centroid。
它选的仍然是大 page，但分数来自 page 内最相关的 sub-block。
它会先平均 query/head，但历史摘要不是一个 page 一个代表，而是一个 page 里多个 sub-block 代表。
它和 QUEST 的主要区别：求和前先屏蔽一部分特征维，避免某些低信号通道影响选块。
这个策略适合记成“先画平均线，再挑高出平均线最多的 page”。
这个策略不只看当前 token 的分数，还把之前步骤的选择倾向保存在 cache 里。
它比普通 centroid 多看了 value：value 能量低的历史块会被 gate 压低。
所以“是否对 H_q 平均”不是公共规则。`BlockSparseAttention` 和 `LServeCentroidSparseAttention` 会先平均 query/head；GQA 系列更常见的是每个 head 分开打分后合并；QUEST 系列核心是 max/min 包络，不是 centroid。

第一段代码应该怎么读

from ..indexer import ...这些算子只在 `forward_indexer` 里用，用来给历史块打分和 topK。
from ..cache import ...带 `C` 前缀的算子通常在 `forward_cache` 里用，用来更新仓库摘要。
@register("...")给策略起运行时名字，配置里会用这个名字选策略。
__init__提前创建算子对象。注意同语义算子也不能复用，因为每个对象有自己的内部缓冲。
create_cache只声明额外摘要张量形状，不包括框架自动提供的 `k` / `v`。
forward_cache定义摘要怎么从 `k` / `v` 算出来。
forward_indexer定义如何打分、如何把 topK 结果写进输出。

flow.py 解决的问题

`flow.py` 不写具体策略，它像一份“策略合同”。`algorithms.py` 里的每个策略类，都必须按这里规定的格式回答三个问题。

策略基类class vFlow(ABC)

所有普通 K/V 策略都继承它。你可以把它理解成“选块策略模板”。

策略输入q / cache / ctx

`q` 是当前 attention 想找什么，`cache` 是历史仓库摘要，`ctx` 是本轮草稿纸和配置。

策略输出o

`o` 不是模型输出文字，而是“挑出来的历史块编号”。后端再按这些编号去读历史。

最容易混的点：cache 有两种视角

forward_cache 看到的 cache更新仓库摘要
按本轮请求看

形状可以粗略记成 `[B, r, c]`。`B` 表示这批请求里哪些块刚受影响。

做的是刷新

比如当前块 K/V 变了，就重新算这块的 centroid、max/min、value 能量。

forward_indexer 看到的 cache挑历史块
按候选历史页看

形状可以粗略记成 `[S, r, c]`。`S` 表示这一轮可选择的历史页。

做的是打分

拿 query 去和每个历史页摘要比较，最后把选中的页写进 `o`。

同一个历史仓库，在“更新摘要”和“挑历史”时会被看成不同布局。这个映射不是策略类自己手写，主要由 `ctx` 和运行时元数据处理。

flow.py 建议阅读顺序

class vFlow先看大 docstring，知道这个文件规定的是“策略接口”。

flashinfer.py 先明确一件事

这个文件不是 FlashInfer 库本体，而是 Vortex 接到 SGLang/FlashInfer 的“适配器”。它负责准备草稿纸、调用编译好的选块工具，再把结果交给 FlashInfer 真正算 attention。

不是策略文件forward_indexer 不在这里写

具体怎么打分选块，在 `algorithms.py` 的策略类里。

是运行时入口VortexFlashInferBackend

它决定什么时候 plan、什么时候更新 cache、什么时候调用 compiled_indexer。

是后端包装BatchDecodeWithPagedKVCacheWrapper

最后真正 attention 计算交给 FlashInfer wrapper。

读取仓库
`get_cache(layer.layer_id)` 拿到 K/V 和摘要

这里拿到的是后面 indexer 和 attention 都要用的历史仓库视图。

down
挑历史
`compiled_indexer.forward(q, o, cache, ctx)`

读 query、仓库摘要和草稿纸，把选中的 sparse 历史页写到 FlashInfer wrapper 会读取的 buffer 里。

down
算 attention
`decode_wrappers[1].forward(...)`

FlashInfer 根据 sparse indices 去读选中的 K/V 页，算出 attention 输出。

所以这页和前面的概念图一致：草稿纸先 plan；当前 K/V 入库并更新摘要；再用 `compiled_indexer` 挑历史；最后 attention 预测下一个 token。

草稿纸和仓库在这里怎么出现

草稿纸：ctx.metadata每轮会改
`MetaData.preallocate(...)`

启动时先分配一大块可复用 buffer。

`plan_decode(...)`

每个 batch 把这轮请求的 indptr、indices、last_page_len 等写进去。

`compiled_indexer.forward(...)`

继续把 sparse 选择结果写到这里，给 FlashInfer 读。

仓库：token_to_kv_pool历史会增长
`set_kv_buffer(...)`

把当前 token 的 K/V 写进历史仓库。

`compiled_cache.forward(...)`

按策略刷新这块历史的摘要。

`get_cache(...)`

把 K/V 和摘要交给 indexer、attention 使用。

最短记法：`ctx.metadata` 是本轮草稿纸；`token_to_kv_pool` 是长期历史仓库。`compiled_indexer` 不“包含”仓库，它是拿仓库和草稿纸来计算。

flashinfer.py 建议阅读顺序

__init__先找 `block_size`、`decode_wrappers`、`plan_decode`、`self.ctx`，知道工具在哪里创建。
