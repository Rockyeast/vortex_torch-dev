普通 K/V 策略可视化

每个策略都还是三问法：存什么摘要、怎么用 query 打分、怎么 topK。区别在于“摘要长什么样”和“多个 head / sub-block / 特征维怎么合并”。

这是最基础的 centroid 策略：每块历史存一个平均 key，当前 query/head 先平均，再和所有历史块代表比相似度。
对：中间先得到 H_q × page 数个分数。之后才把多个 head 对同一个 page 的分数合并，变成每个 page 一个最终分数，再 topK。
QUEST 的核心是“这个历史块最多可能多相关”，所以存的是每个维度的 max/min，而不是 centroid。
它选的仍然是大 page，但分数来自 page 内最相关的 sub-block。
它会先平均 query/head，但历史摘要不是一个 page 一个代表，而是一个 page 里多个 sub-block 代表。
它和 QUEST 的主要区别：求和前先屏蔽一部分特征维，避免某些低信号通道影响选块。
这个策略适合记成“先画平均线，再挑高出平均线最多的 page”。
这个策略不只看当前 token 的分数，还把之前步骤的选择倾向保存在 cache 里。
它比普通 centroid 多看了 value：value 能量低的历史块会被 gate 压低。
所以“是否对 H_q 平均”不是公共规则。`BlockSparseAttention` 和 `LServeCentroidSparseAttention` 会先平均 query/head；GQA 系列更常见的是每个 head 分开打分后合并；QUEST 系列核心是 max/min 包络，不是 centroid。

abs/ 抽象层

这一层回答“为什么调用算子时不是马上算，而是在 trace/profile 阶段记录图”。

abs/op.pyvOp 基类：profile / execute / __call__
abs/tensor.pyvTensor：只有元数据，没有真实 GPU 数据

indexer/ 算子层

这些文件多数套路相同：检查输入形状 -> 推导输出 vTensor -> 把 op/tensor 关系写进 ctx。

matmul.pyGeMM：query 与摘要打分
reduce.pyMean / Max / Sum 等聚合
scan.pySoftmax / Normalize
output_func.pytopK / approxTopK 输出 page ids
elementwise / mask / kron / reshape / transpose / save_load辅助变换、屏蔽、保存/读取 running state

ctx / metadata 运行上下文

这一层回答“草稿纸在哪里、图结构列表在哪里、FlashInfer/TRTLLM 为什么格式不同”。

context.pyctx 本体：参数 + 计算图列表
metadata.py每轮 batch 草稿纸：indptr / indices / workload
select.pyTRTLLM block_table + seqlens 输出
utils_sglang.py加载底层 module，返回工具函数

indexer/compiler/graph.py

当前文件。它不做数学计算，而是把 ctx 草稿图整理成 compiler 能吃的 full_graph 和 subgraphs。

UnionFind / OpDAG / SubgraphDAG分组、op 依赖图、subgraph 环检查
_build_op_dag下一块：筛选活 op + 建 op 依赖图
_fuse_w_ops融合 W 算子，减少 kernel 数
_build_all_graphs / _build_local_graph / contruct_graph分组、拓扑排序、global id 重编号为 local Graph
